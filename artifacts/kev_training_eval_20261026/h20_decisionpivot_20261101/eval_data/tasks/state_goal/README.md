# state_goal

Generated file-store traces: after these operations, are all goal conditions satisfied?

- Decision: whether, after an agent's numbered trace of set / delete / rename / copy / move steps on a small file store, every goal condition on the final tree holds (yes) or at least one fails (no).
- Item source: generated by `build/gen_state_goal.py` (`random.Random(20261007)`, standard library only, no input file); labels programmatic; licence: generated by the benchmark's script (no third-party text); items included.
- Rows: 600 (300 yes, 300 no); metric: accuracy (chance 0.5). Rebuild: `python3 build/gen_state_goal.py`.

## What is generated

Each state names the kind of store (five domains, `meta.domain`: office reports, software project, data analysis, website, course material), states what every step did, shows the files of a small folder tree at the start (path and a one-word status as content), one line for each kind of step saying what it does (including what happens when the target path is taken), a goal of 3, 5 or 7 conditions on the final tree (a file exists or does not, a file holds a word, a folder holds N files directly, two files hold the same word) and a numbered trace of the steps an agent ran. Every step finds its file and changes the tree, so no step looks wrong on its own. The 300 positives reach the goal; each has a twin in which one operation of the trace is changed so that exactly one goal condition fails. The file list has four layouts, the goal four wordings, the trace four notations and four numberings. Both rows of a pair are scored as separate items; they share `group` (= `meta.pair`), so a bootstrap that resamples by `group` accounts for their correlation and the audit keeps a pair in one fold.

## What every step did (the preamble)

The state says, in four phrasings: *every delete, rename, copy and move found its source file; set creates the file or replaces its content; every step changed the store.* The generator asserts this for every step of all 600 traces, and `check(item)` asserts it again on the parsed text, so a solver can rely on it. (In benchmark v0 / v1 the sentence claimed that the file each step works on existed, which was false for a `set` that creates a file.)

## Names, contents and goal-directed traces

File and folder names are ordinary names of the domain (`reports/q3_summary.md`, `data/customers_2026.csv`, `logs/app.log`, `releases/v2.1`, `drafts/lecture_02_draft.md`); contents are status words (`draft`, `review`, `approved`, `final`, `outdated`, `archived`, `v1`, `v2`, `raw`, `clean`, `validated`, `default`, `custom`, `stable`, `empty`, `debug`, `warnings`, `errors`, `cache`, `partial`, `stale`, `scratch`). A rename stays inside one file family and keeps the extension; a file is only moved or copied into a folder that takes files of its kind (a `.tmp` file never goes to the archive); a content word fits the kind of file. The generator asserts this (`plausible`) for every step of every trace, planted deviations included, so a changed step does not look odd by itself. It also asserts that every trace, planted deviations included, can be cut into whole macros (`coherent`): the planted change is a wrong choice inside valid macros (the wrong file archived, the wrong status written, two macros in the wrong order, a macro left out), never a broken macro, so the deviation cannot be found by looking at the structure of the trace. The trace is a sequence of *macros*, short purposeful sequences of 1 to 3 steps; every step belongs to a macro (`meta.spec.macros` names the macro of each step). Steps that no goal condition looks at are macros too (distractors that look purposeful). Goal conditions preferably state what a macro was meant to achieve. Macros (number of steps in the 300 positive traces):

| macro | what it does | steps |
|---|---|---|
| archive | archive an old or finished file that was there at the start: move it into the archive folder (sometimes after setting its content to `archived`, or as copy + delete) | 1023 |
| publish | publish a final version: set the content to `final` (or `validated` for data) and copy the file to the publication folder, copy or move a file that is already final, or rename a draft to final and move it there | 757 |
| finalize | rename `name_draft.ext` to `name_final.ext` and set the content to `final` | 354 |
| cleanup | clean up temporary files: delete one to three `.tmp` files | 187 |
| obsolete | remove a file whose content says `outdated` | 67 |
| backup | back up before overwriting: copy the file to the backup folder, then write a newer content to the original | 704 |
| restore | copy a file back from the backup folder to the folder where it is kept (replacing the file there) | 143 |
| rotate | rotate a log: rename `x.log` to `x_old.log`, then create an empty `x.log` | 74 |
| version | make a new version: copy the file to `name_v2.ext` and mark the copy (`draft` for documents, `v2` otherwise) | 357 |
| status | advance the status of a file along draft - review - approved - final (raw - clean - validated, default - custom - stable) | 421 |
| newfile | create a new file with its first status (a draft, a raw data file, a default setting, an empty log) | 324 |

## Dial

`meta.level` = 1, 2, 3 = `meta.steps` = number of steps of the trace: 5, 15, 25 (200 rows each, 100 yes and 100 no). The start tree has 6-8, 8-12 and 11-15 files and the goal 3, 5 and 7 conditions. Each domain has 40 rows per level.

## Deviation kinds (`meta.deviation`, number of no-items per level)

| kind | formerly (v0, v1) | what is changed | level 1 | level 2 | level 3 | total |
|---|---|---|---|---|---|---|
| wrong_target | wrong_key | one step acts on the wrong target: one path, new name or folder of one step is replaced by another one of the same kind that occurs in the item (a sibling file, the same file name in another folder, another folder that takes such files) so that the step is still a valid macro step; the failing goal can be of any type, a folder count included | 25 | 25 | 25 | 75 |
| wrong_content | wrong_value | the content word of one `set` step is replaced by another word that fits the file | 25 | 25 | 25 | 75 |
| steps_swapped | swap | two steps (at most four places apart) exchange their places and the order matters (the trace stays a sequence of whole macros) | 25 | 25 | 25 | 75 |
| step_missing | missing | one step is left out and an unrelated single-step macro is inserted elsewhere (the trace keeps its length) | 25 | 25 | 25 | 75 |

`meta.failed_condition` is the number of the goal condition that fails; its type is in `meta.failed_type`. With `wrong_target` the failing condition is often a folder count or a missing file, because the step acted on another file than intended; the name says what went wrong in the trace, not which kind of condition fails.

State length: 1514 to 4246 characters (median 2475).

## Checks run by the script

- `truth(spec)` (simulation on a dict of paths) and `check(item)` (parses the state text and simulates on a folder tree) agree on all 600 items; every negative fails exactly one condition and still runs every step; a pair differs only in the changed operation.
- The preamble holds for every step of every trace (source file found, set creates or replaces, every step changes the store); every step is plausible; every rename keeps its extension; every trace (yes and no) can be cut into whole macros.
- Exact balance: 300 yes / 300 no; 100 + 100 per level; 25 deviations per kind and level; 40 rows per domain and level. No change adds or removes a word of the state; every word of a goal occurs in the start list or the trace.
- Every file or folder named by a goal condition is touched by at least one step of the trace (sources and resolved move / rename / copy targets; a `same` condition: one of its two files) in all 600 items, so an untouched condition never marks a negative. The left-out step of `step_missing` is never the only step that touches the failing condition's target, and the inserted step never touches it.
- The number of steps outside the dependency cone of every goal condition (walking back from the goal, a step is live when it writes a file that a condition or a live step needs, or a file directly inside a folder of a count condition) is equal in the two members of every pair; mean per item, yes / no, level 1: 0.91 / 0.91, level 2: 3.48 / 3.48, level 3: 4.44 / 4.44.
- Vocabulary test: no word (and no token) of frequency >= 20 is more than twice as frequent in one class as in the other.

## Examples (one per level)

### level 1, steps = 5 (state_goal:00075, office, deviation wrong_target, failing condition G1)

```
STATE:
Below are the starting files of a small file store, the goal an agent was given, and the steps it ran. The store holds the quarterly reports and working papers of a small office. Every delete, rename, copy and move found its source file; set creates the file or replaces its content; every step changed the store.

At the start the store holds these files and contents:
  backup/meeting_notes.txt (v1)
  drafts/meeting_notes_draft.txt (draft)
  drafts/q2_summary_draft.md (approved)
  published/meeting_notes.txt (v1)
  published/risk_register.md (final)
  reports/meeting_notes.txt (final)
  tmp/cache.tmp (stale)

How each kind of step works:
  set: puts the content into the file at the path, whether or not the file exists yet; an existing file loses its old content.
  delete: erases the file at the path from the store.
  rename: new name, same folder; when the new name is taken, the other file is replaced.
  copy: the destination path receives the source's content (replacing any file there); the source is not changed.
  move: relocates the file to the folder, keeping its file name; an existing file with that name in the folder is overwritten.

Goal (all conditions must hold after the last step; a folder's file count includes only the files directly inside it):
  G1. drafts/q1_summary_draft.md holds draft
  G2. there are 0 files in tmp
  G3. backup/meeting_notes.txt and reports/meeting_notes.txt are identical in content

Steps run by the agent, in order:
  1. {"op": "copy", "source": "backup/meeting_notes.txt", "destination": "reports/meeting_notes.txt"}
  2. {"op": "delete", "path": "tmp/cache.tmp"}
  3. {"op": "set", "path": "drafts/q1_summary_draft.md", "content": "draft"}
  4. {"op": "set", "path": "drafts/q1_summary_draft.md", "content": "review"}
  5. {"op": "copy", "source": "reports/meeting_notes.txt", "destination": "reports/meeting_notes_v2.txt"}

QUESTION: After these operations, are all goal conditions satisfied?
OPTIONS:
  yes: Every goal condition holds after the last step.
  no: At least one goal condition does not hold after the last step.
GOLD: no
```

## Relation to the authors' training data

The items are disjoint from any training generator of the authors by construction: this is a new generator, written for this benchmark (its own templates, its own vocabulary of ordinary file and folder names and status words, its own macros).
